Going live with Runwell

From an empty server to a live Runwell on Hoster, with a Rails install brought over if you have one. One install per app; repeat for each business.

The one rule: every install keeps everything (database, uploaded files, secret key) in its own volume at /data. The repository's config/deploy.yml sets that up, and Runwell refuses to start without it, so a deploy can't wipe an install.

Before you start

  • Hoster is connected to GitHub with access to Martin-Business-Consultants/runwellgo.
  • The server is set up in Hoster.
  • Runwell's domain (e.g. crm.brem.io) points at the server: a DNS A record to its IP.
  • Moving from the Rails core? A backup from its Settings › Export › Make a backup (a .zip).

Go live

  1. Create the app In Hoster: New app, from the GitHub repository Martin-Business-Consultants/runwellgo, branch main.
    • Name it after the business, e.g. brem. The name becomes its volume: brem-data.
    • Every install needs a name of its own. Never reuse one.
  2. Add the domain Domains › Add domain: crm.brem.io. Hoster takes care of HTTPS.
  3. Set the variables Under Variables:
    NameValue
    SITE_KEYbremRecommended. The install's name: the first start records it in the volume, and a container with a different one refuses that volume, so two installs can't share a database by mistake. Without it nothing is checked.
    APP_URLhttps://crm.brem.ioOptional. Settings › Address takes over once set.
    SMTP_ADDRESS …Optional. Or set email up in Settings › Email.
    Port 80, the /up health check, TRUST_PROXY and the volume come from the repository. Don't add them by hand.
  4. Deploy Press Deploy. When it's done, Logs shows runwell is up, and Volumes lists brem-data at /data.
    If the log says the data directory isn't on a persistent volume, the volume didn't apply. Check that the app is deploying from main (the repository's config/deploy.yml) and deploy again. Nothing has been lost; Runwell stopped before writing anything.
  5. Make the first owner Open https://crm.brem.io.
    • Moving from Rails? Make a first owner on the sign-up screen (it's replaced in the next step), then carry on.
    • Starting fresh? The account you make here is the owner. Skip step 6.
  6. Bring the Rails install in Settings › Import: upload the backup, read what it found, and import. Runwell restarts onto it, and everyone signs in with the passwords they had. Switch your plugins back on in Settings › Plugins (and paste the AI provider's key again in Settings › AI).
  7. Turn on backups In Hoster, Backups: set a backup schedule (nightly) for brem-data, then press Back up now once to see it work. Settings › Export also makes a backup any time.
  8. Finish setting up Home's Get set up list walks through the rest: Settings › Address (the address emails link to, and the time zone), Email, inviting the team.

Working on it with AI agents

On your own machine, with the same runwell program:

runwell login https://crm.brem.io     # approve it in the browser
runwell briefing                     # what needs a person now
runwell mcp setup                    # the line to add it to Claude Code, Codex, Cursor…

Every install is an MCP server at /mcp too (and /portal/mcp for a client's own agent). Code work goes to a runner on a machine you control: docs/runners.md.

Updating

  1. See what's new Settings › Updates says when a new version is out, with its notes (the GitHub release).
  2. Back up Hoster Backups › Back up now (the update takes its own too).
  3. Update Press Update now in Settings › Updates. It takes a backup into the install's own volume (/data/backups/), downloads the new version there (checked against the release's checksums), and restarts on it: a few seconds offline. The database updates itself on start. If the new version doesn't come up, Runwell goes back to the one before and says so.

Each install updates on its own, from its own volume. Deploying a newer image from Hoster works too, and takes over from an update made with the button. To go back, deploy the previous version from Hoster; if a release's notes say it changed the database, restore the backup from /data/backups/ (Settings › Import) instead.

Making a release

Releases are what Settings › Updates and install.sh offer. From a clean main with the app built (make ui, committed in internal/admin/dist):

echo 3.1.0 > VERSION && git commit -am "Release 3.1.0"
git tag v3.1.0 && git push origin main v3.1.0

The release workflow tests, builds every platform's runwell and runwell-runner with checksums.txt, and publishes the GitHub release; installs see it within the hour. The repository must be public (or Settings › Updates can't read its releases).

Several installs on one server

Each install gets its ownExample
App (and so volume)brem → brem-data, acme → acme-data
Domaincrm.brem.io, crm.acme.com
SITE_KEYbrem, acme
Backup scheduleone per volume

The first start records SITE_KEY in the install's volume. A container with a different SITE_KEY refuses that volume, so two installs can't end up sharing one database by mistake.

If something goes wrong

You seeWhat to do
Deploy fails: target failed to become healthyOpen Logs. Runwell prints one line saying why it stopped. The usual ones are below.
the data directory isn't on a persistent volumeDeploy from main (it has config/deploy.yml) and check Volumes. For a throwaway trial only: EPHEMERAL_DATA=1.
the data directory belongs to another siteTwo installs are pointed at one volume. Give each app its own name, or fix SITE_KEY.
Emailed links point at localhostSet Settings › Address (or APP_URL).
Locked outHoster Shell: runwell user password --email you@example.com --password -, then type the new password.
